# 05 · Migrations and vector index (`fix/migrations-and-vector-index`)

## Concept: what Alembic migrations are
The database schema is code. Each migration file is one step (`upgrade()` / `downgrade()`) with a `revision` id and a `down_revision` pointer to the step before. Together they form a chain, and `alembic upgrade head` replays it on a database. The table `alembic_version` stores which step a database is at.

## Bug: the chain didn't work on a fresh database
- The history **forked** (`c96bd…` had two children) and was later merged with an empty "merge heads" migration.
- `chunk` was created in `2f7fda260737`, and an **autogenerated** migration `971acdcdd25c` created it **again**. Autogenerate compares models to *the author's* database at that moment; that database was in a different state, so the generated step was wrong for everyone else.
- Result on a new DB: `DuplicateTable: relation "chunk" already exists`.

## Fix: squash into one baseline
No database depended on the old history (yours had never been created), so all 14 files were replaced by **one baseline** generated from the models (`4838f20e2a7a_baseline_schema.py`). It's common to do this before a project's first real deployment. **After** a real deployment, you never rewrite history; you only add new migrations.

Steps used:
```bash
git rm migrations/versions/*.py
# reset the half-built DB
docker exec postgres-container psql -U ai_user -d ai_agent_db -c "DROP SCHEMA public CASCADE; CREATE SCHEMA public;"
alembic revision --autogenerate -m "baseline schema"
# review it! autogenerate is a draft: added `import pgvector.sqlalchemy` and CREATE EXTENSION vector
alembic upgrade head
alembic check          # "No new upgrade operations detected" = models and DB match
```
`migrations/script.py.mako` (the template for new migrations) now imports pgvector, so future autogenerated files work as they are.

## Lesson: declare indexes and keys in the model
The HNSW indexes previously existed only in hand-written migrations, so models and DB could drift apart. Now they're in `__table_args__` on `Chunk` and `Memory`, and `alembic check` verifies they match.

## Bug: index metric ≠ query metric
pgvector has one operator per distance: `<->` L2, `<=>` cosine, `<#>` inner product. An HNSW index is built for one of them (`vector_l2_ops`, `vector_cosine_ops`, ...). Postgres can only use the index when the query's `ORDER BY` uses the **same** operator.

- `chunk` index: cosine. Query in `retriever.py`: L2, so the index was never used.
- Proof with `EXPLAIN`:
  - cosine `<=>` → `Index Scan using chunk_embedding_idx`
  - L2 `<->` → `Seq Scan` + `Sort` (reads every row)
- Fix: `Chunk.embedding.cosine_distance(...)`. Cosine is the standard for text embeddings because it compares *direction* (meaning), not length.
- `memory` already matched (L2 index + L2 query), so it stays L2. Its thresholds are tuned for L2 distances.

## Bug: orphan chunks
`chunk.file_id` was a plain UUID column. Deleting a file left its chunks, and their embeddings, behind forever. It's now `ForeignKey("file.id", ondelete="CASCADE")` plus an index (we filter by `file_id` on every search).

## Bug: `str(None)` is truthy
```python
str(metadata.get("section_id")) or str(metadata.get("sheet")) or ...
```
`str(None)` gives `"None"`, a non-empty string, so it's truthy and the `or` chain stopped at the first key every time. All non-PDF chunks were grouped under one section, "None". The fix checks `is not None` *before* converting.
